# v2/ — Confirmation Run

This directory is a clean-break reimplementation of the federal-survey-concept-mapper pipeline against the USAi-routed model ensemble via `usai-harness`. The original v1 work in the parent directory remains untouched and frozen; v2 is built independently to test whether the v1 findings reproduce under a different LLM ensemble routed through different transport.

## What v2 Is

A parallel pipeline. Same prompts, same input data, same downstream stages. Different LLM ensemble. Different transport. Independent codebase under `v2/`.

The reproducibility claim v2 supports is "v1's classifications and harmonization findings hold up when the methodology is re-implemented by a different team using a different model ensemble through a different transport." If v2 reproduces v1's headline metrics within reasonable tolerance, that's strong evidence the methodology is robust to ensemble substitution. If v2 diverges, that's data about what depends on the ensemble.

## What v2 Is Not

- Not a fork. Same git repo, same history, just a parallel subtree.
- Not a replacement for v1. v1 is frozen. The validated v1 outputs stay.
- Not a retroactive re-run. v2 produces its own outputs, written under `v2/output/`.
- Not a methodology revision. Prompts, batch sizes, taxonomy, sample frame — all byte-identical to v1.

## What's Committed vs Generated

**Committed (authored once on a dev machine, lives in the repo):**

- `README.md`
- `data/raw/*`
- `src/`

**Generated locally per machine (every user runs `usai-harness project-init` once):**

- `usai_harness.yaml`
- `output/`
- `tevv/`
- `scripts/`

This matches how every harness consumer will work. Nothing about v2 is special.

## Dependency Surface

v2's runtime dependencies are exactly:

- `usai_harness` (≥0.3.0)
- `pandas`
- Python standard library

No `anthropic`, no `openai`, no `dotenv`, no `tqdm`. Anything v1 imports because v1 used vendor SDKs directly is irrelevant to v2.

If a v2 script needs another package, the package must already be in the local Python environment.

## The v2 Pool Configuration

After running `usai-harness project-init` (see "Bootstrap Procedure" below), the generated `usai_harness.yaml` is a single-rater placeholder. Replace its contents with:

```yaml
project: concept_mapper_v2
provider: usai
workers: 4

models:
  - name: gemini-2.5-flash
    temperature: 0.1
  - name: claude_4_5_sonnet

default_model: gemini-2.5-flash

ledger_path: output/cost_ledger.jsonl
log_dir: output/logs
```

### Why these models

- `gemini-2.5-flash` and `claude_4_5_sonnet` are the two raters used for v2 Stage 1 classification, providing inter-rater independence across model families (Google × Anthropic).
- Available models on USAi (as of 2026-04-29): `claude_4_5_opus`, `claude_4_5_sonnet`, `gemini-2.5-flash`, `gemini-2.5-pro`, `llama_4_maverick`. Pool selection prioritizes architectural diversity at moderate cost.
- Names are USAi-specific and do not match vendor canonical names. Verify against the local catalog with `usai-harness list-models --provider usai --format names` before pasting.

### Why these parameters

- Gemini Flash gets `temperature: 0.1`. Slight stochasticity over `0` to avoid mode-locking.
- Sonnet has no `temperature` field. Anthropic models on the USAi-routed Anthropic-compatible interface do not accept the parameter; sending it would fail. Per harness 0.3.0 (ADR-012 amendment), parameters absent from the config are not sent on the API call.
- `workers: 4` is the harness worker count for parallel calls.

## Bootstrap Procedure

Run once per machine. Same procedure every harness consumer runs for any new project.

### Pre-requisites

- `usai-harness` 0.3.0 or higher installed in the active Python env.
- USAi credentials configured at the user-level config location (set by `usai-harness init`). Verify with `usai-harness ping`.
- Repo pulled to the latest main.

### Steps

1. `cd v2`

2. `usai-harness project-init`

   Generates `usai_harness.yaml`, `output/`, `tevv/`, `scripts/`, and runs a TEVV smoke test against the user-level default model. The TEVV report at `tevv/init_report_<UTC_timestamp>.md` must show `**Verdict:** PASS` before continuing.

3. Replace the contents of `usai_harness.yaml` with the v2 pool YAML shown in "The v2 Pool Configuration" section above. Save.

4. Run the smoke test:

   ```
   python src/core/t3_smoke_test.py
   ```

5. Read the verdict at `output/t3_smoke/t3_smoke_report.md`.
